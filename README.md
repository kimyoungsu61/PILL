# PILL

[![PILL CI](https://github.com/kimyoungsu61/PILL/actions/workflows/ci.yml/badge.svg)](https://github.com/kimyoungsu61/PILL/actions/workflows/ci.yml)

영양제 라벨 분석과 복용 루틴을 관리하는 앱입니다. Expo 웹 앱과 Spring Boot API를 하나의 Docker 이미지로 배포합니다.

- 라벨 이미지 분석, 회사·제품·성분 정보 확인 및 수정
- 영양제 등록·삭제, 1분 단위 복용 시간 설정
- 복용 완료·취소와 복용 기록 관리
- 홈 화면에 설치하는 웹 앱과 복용 알림
- Gemini 기반 제품 정보와 복용 안내
- 촬영 대상 구분과 비영양제 안내, 영양제로 확인된 분석 결과만 등록
- 검색으로 확인한 제품 대표사진을 오늘의 복용·영양제 목록에 표시

## 구성

| 경로 | 내용 |
| --- | --- |
| `app/` | Expo · React Native · TypeScript 앱, PWA 파일, 계약 테스트 |
| `server/` | Java 21 · Spring Boot API, MySQL 스키마, 서버 테스트 |
| `Dockerfile` | 웹 빌드 → 서버 패키징 → 실행 이미지 |
| `compose.local.yaml` | PC에서 앱과 개발용 MySQL 실행 |
| `.github/workflows/ci.yml` | 앱·서버 검사 후 배포용 Docker 이미지 빌드 |

## PC에서 Docker로 실행

Node.js 24와 실행 중인 Docker Desktop이 필요합니다.

```sh
node scripts/setup-local.mjs
docker compose -f compose.local.yaml up --build --detach --wait
```

브라우저에서 http://localhost:18082 를 열고 개발용 계정을 만듭니다. 로컬 설정은 `.local/docker/`에 생성됩니다. 스크립트를 다시 실행해도 기존 비밀번호를 덮어쓰지 않습니다.

Gemini 이미지 분석을 사용하려면 최초 설정 전에 `GEMINI_API_KEY` 환경 변수를 지정하거나, 생성된 `.local/docker/GEMINI_API_KEY` 파일에 본인의 키를 저장합니다. 키를 설정하지 않아도 수동 등록과 복용 기록 기능을 사용할 수 있습니다.

```sh
docker compose -f compose.local.yaml logs --tail=100 app
docker compose -f compose.local.yaml down
```

중지해도 MySQL 볼륨에 저장한 기록은 유지됩니다. 로컬 환경에서는 웹 푸시를 끕니다.

## 로그인 유지

아이폰 홈 화면 웹 앱은 HttpOnly·Secure·SameSite 쿠키로 로그인한 날부터 최대 180일 동안 로그인을 유지합니다. 로그인 비밀 값은 웹의 localStorage에 저장하지 않습니다. 네이티브 빌드는 기기 보안 저장소를 사용합니다.

기존의 유효한 웹 로그인은 앱을 다시 열 때 같은 서버 세션으로 이전하므로 연결된 복용 알림을 유지합니다. 앱을 열 때마다 만료일을 연장하지 않으며, 로그아웃하면 서버 세션을 무효화하고 기기에 로그아웃 상태를 남깁니다. 지연된 응답이 다른 탭의 새 로그인 쿠키를 지우지 않도록 일반 조회·로그아웃·탈퇴 응답에서는 쿠키를 덮어쓰지 않습니다. 브라우저에 남은 폐기된 쿠키는 인증에 사용할 수 없습니다. 일시적인 네트워크 오류는 저장된 로그인을 지우지 않습니다. 오프라인에서 로그아웃한 경우에는 자동 로그인 복원을 막고, 다음 실행에서 서버 무효화를 다시 시도합니다.

쿠키를 사용하는 변경 요청은 앱 전용 헤더와 동일 출처 검증을 거칩니다. 로그인 유효기간은 `pill.auth.session-ttl`로 설정합니다.

## 계정 관리

설정 → 내 계정에서 이메일 인증과 비밀번호 재설정, 회원 탈퇴를 관리합니다. 기존 계정은 인증 전에도 계속 사용할 수 있습니다. 로그인 화면에서도 비밀번호 재설정을 시작할 수 있습니다.

인증번호는 6자리·10분 유효·일회용이며, 5회 오류 후 새 번호를 받아야 합니다. 서버에는 번호 원문을 저장하지 않습니다. 같은 이메일의 인증·복구 요청을 합해 60초 간격, 시간당 5회, 하루 10회로 제한하며 IP 제한도 적용합니다. 비밀번호 찾기 요청은 가입 여부와 관계없이 같은 안내를 반환합니다.

비밀번호 변경은 기존 모든 로그인 세션과 웹 알림 연결을 무효화합니다. 기록과 영양제는 유지하며, 새 비밀번호로 로그인한 뒤 알림 설정에서 이 기기를 다시 연결해야 합니다. 로그인과 변경이 동시에 진행돼도 이전 비밀번호로 발급된 세션은 남지 않습니다. 세션 복원은 폐기된 세션을 다시 활성화하지 않습니다.

회원 탈퇴는 현재 비밀번호와 ‘탈퇴’ 확인 문구를 요구합니다. 해당 계정의 영양제·복용 기록·실패한 분석을 포함한 스캔 기록·정원·알림·인증 정보·모든 세션을 한 트랜잭션으로 삭제합니다. 실패하면 전체를 되돌리고 다른 계정의 기록은 건드리지 않습니다.

### 무료 메일 발송 연결

Brevo의 HTTPS transactional API를 사용합니다. Railway의 `pill-web` 서비스에 다음 비밀 변수를 설정합니다. 키를 소스·GitHub Actions·클라이언트 빌드에 넣지 않습니다.

| 변수 | 값 |
| --- | --- |
| `PILL_ACCOUNT_MAIL_API_KEY` | Brevo API 키. SMTP 키와 다릅니다. |
| `PILL_ACCOUNT_MAIL_FROM` | Brevo에서 확인한 발신 이메일 주소만 입력. 표시 이름은 PILL로 고정됩니다. |

Brevo 무료 가입 → 본인 이메일 확인 → Settings의 Senders에서 발신자 이름 PILL과 본인 주소 등록·확인 → transactional 발송 활성화 확인 → Railway 변수 저장 순서입니다. 자체 도메인이 없으면 Brevo가 임시 `brevosend.com` 발신 주소로 바꿀 수 있습니다. 계정별 발송 승인·수신함 도착은 별도 확인해야 하며, API 수락을 실제 도착으로 간주하지 않습니다. 무료 한도와 승인 조건은 [Brevo 공식 안내](https://help.brevo.com/hc/en-us/articles/208580669-FAQs-What-are-the-limits-of-the-Free-plan)를 확인합니다.

변수가 없으면 계정 조회·탈퇴는 동작하고, 인증·복구 화면에는 준비 중 안내가 표시됩니다. 메일 요청을 성공한 것처럼 표시하지 않습니다. 메일 전송은 DB 커밋 후 제한된 작업 큐에서 진행하고, 발송 실패 시 해당 인증번호만 폐기합니다. 수신 이메일·인증번호·비밀번호·API 키·제공사 응답 본문을 로그에 남기지 않습니다.

API: `GET /api/account/profile`, `POST /api/account/email-verification/request`, `POST /api/account/email-verification/confirm`, `DELETE /api/account`. 로그인 없이 `GET /api/auth/account-config`, `POST /api/auth/password-reset/request`, `POST /api/auth/password-reset/confirm`을 사용할 수 있습니다. 새 메일 테이블은 반복 실행 가능한 `db/account_email.sql`에서 추가하고 기존 세션·복용 기록·알림 키를 보존합니다.

## 촬영 대상 확인

첫 이미지 분석에서 촬영한 중심 대상의 이름과 종류를 먼저 확인합니다. 영양제·주류·음료·식품·의약품·기타·미확인을 구분하며, 배경의 다른 제품이나 포장 모양만으로 영양제라고 판단하지 않도록 요청합니다. 흐린 사진, 여러 대상, 서로 다른 제품의 사진은 추가 촬영이 필요할 수 있습니다. 이 구분은 AI의 추정이며 항상 정확한 식별을 보장하지 않습니다.

술이나 음료 등은 대상에 맞는 짧은 안내와 다시 촬영하기를 보여주고, 영양제 성분·복용 시간 입력은 표시하지 않습니다. 제로·무카페인 음료 등에서 당·카페인 함유를 임의로 단정하거나 함량·음주량을 만들어내지 않습니다. 비영양제와 미확인 결과도 분석 이력으로 보관합니다.

서버는 저장된 최초 분석 결과를 기준으로 등록 가능 여부를 계산합니다. 유효한 인식 정보가 있고 영양제로 분류된 결과만 등록할 수 있으며, 정보 수정이나 클라이언트 요청으로 이 제한을 우회할 수 없습니다. 이전에 분석했지만 대상 구분이 없는 결과는 다시 촬영해야 합니다. 이미 등록된 영양제와 별도의 수동 등록에는 영향을 주지 않습니다.

참고: [Gemini 이미지 이해](https://ai.google.dev/gemini-api/docs/image-understanding), [구조화된 출력](https://ai.google.dev/gemini-api/docs/structured-output), [WHO 알코올 안내](https://www.who.int/news-room/fact-sheets/detail/alcohol).

## 제품 대표사진

대표사진은 등록된 제품의 브랜드·제품명·라벨을 기준으로 찾습니다. 기존에 확인한 검색 출처를 우선 재사용하고, 필요하면 Gemini Google Search로 제품 페이지를 조회합니다. 모델이 작성한 이미지 URL은 사용하지 않으며, 제품명이 일치하는 제조사·판매처 페이지의 Product JSON-LD 또는 Open Graph 사진만 저장합니다. 촬영한 사진과 기기 내부 파일 경로는 목록의 대표사진으로 사용하지 않습니다.

기존 영양제에도 화면을 열 때 비동기로 적용되며 복용 체크를 기다리게 하지 않습니다. 같은 제품의 중복 시간은 검색을 공유하고 동시에 두 제품까지만 조회합니다. 성공한 사진과 출처는 서버에 보관하고, 미확인은 5분, 일시적 조회 실패는 1분 동안 재검색하지 않습니다. 조회 방식이 바뀌면 이전 방식의 실패 결과는 재사용하지 않습니다. 제조사의 짧은 제품 제목과 제품 URL에 명시된 제형·함량·포장 수량을 함께 비교하고, 검색 출처는 최대 8개 확인합니다. 확인되지 않은 제품이나 이미지 로딩 실패는 기존 이니셜로 표시합니다. 공개 페이지 조회는 `ProductImagePageClient`의 제조사·판매처 허용 목록과 HTTPS 리다이렉트 제한을 적용합니다. 원본 라벨·함량·복용 시간·알림은 변경하지 않습니다.

## 후속 알림

웹 앱의 알림 설정에서 기기별로 후속 알림을 켤 수 있습니다. 기존 연결은 꺼진 상태를 유지하며, 기본 제안은 30분 간격·추가 1회입니다. 간격은 1·5·15·30·60분, 추가 횟수는 최대 3회까지 선택합니다. 설정 저장 후 다음 정상 발송된 복용 알림부터 예약합니다. 선택한 쉬는 시간에는 후속 알림과 미룬 알림을 보내지 않으며, 지난 알림을 아침에 몰아서 보내지 않습니다. 원래 복용 알림에는 영향을 주지 않습니다.

알림을 누르면 해당 제품·날짜·시간에 대해 복용 완료, 15분 뒤 다시 알림, 이번 복용 건너뛰기를 선택합니다. 미루기는 복용 기록을 만들지 않으며 대기 중인 추가 알림 시간을 교체합니다. 자동·수동을 합해 한 일정당 추가 알림 발송은 최대 3회입니다. 복용 완료·건너뛰기는 다른 기기의 대기 중인 후속 알림도 취소합니다. 기록을 취소해도 취소한 후속 알림을 되살리지 않습니다.

후속 예약과 발송 결과는 DB에 보관합니다. 발송 직전에 로그인·기기·제품 일정·복용 기록·쉬는 시간·최대 횟수를 다시 확인합니다. 다음 제품 복용 시간이 오거나 예약 시각에서 5분이 지나면 종료해 중단 중 쌓인 알림을 재발송하지 않습니다. 날짜가 바뀐 뒤에도 원래 일정의 날짜로 기록합니다. 추가 테이블만 생성하며 기존 복용 데이터, 알림 구독, VAPID 키와 세션을 보존합니다.

## 자동 검사

`main`으로 push하거나 `main` 대상 pull request를 만들면 GitHub Actions가 실행됩니다.

1. 앱 의존성 설치, 테스트, TypeScript 검사, 웹 export
2. 서버 테스트와 JAR 패키징
3. 두 검사 통과 후 실제 배포용 Docker 이미지 빌드

검사에는 운영 DB, Gemini API 키, 복용 기록이 필요하지 않습니다. Actions에 운영 비밀 값을 저장하지 않습니다. Actions 버전은 커밋 SHA로 고정하고 Dependabot이 월 단위 업데이트를 제안합니다.

수동 검사:

```sh
cd app
npm ci
npm test
```

```sh
cd server
mvn --batch-mode --no-transfer-progress verify
```

## Railway 배포

기존 PILL 서버는 이 저장소의 `main`에 연결되어 있으며 **Wait for CI**가 켜져 있습니다. main 커밋의 GitHub Actions 검사가 통과하면 Railway가 자동 배포합니다. Dockerfile과 `railway.toml`은 저장소 루트에 있습니다.

DB 연결, Gemini 키, 웹 푸시 VAPID 키는 Railway 서비스 환경 변수로 관리합니다. MySQL은 별도 서비스와 영구 볼륨을 사용합니다. 웹 푸시는 HTTPS 환경과 사용자 알림 허용이 필요하며, 아이폰에서는 홈 화면에 설치한 웹 앱에서 사용합니다.

운영 데이터와 계정, 이미지 원본, 실패한 분석 기록, 개인 PC 설정 및 키 파일은 이 소스 저장소에 포함하지 않습니다.
